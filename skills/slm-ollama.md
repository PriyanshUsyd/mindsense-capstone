# Skill: SLM Integration (Ollama + Pinned Local Candidates)

Applies to: SLM Integration Lead primarily.

## The model candidates

Ollama is the confirmed local runtime. `phi4-mini:3.8b` is the pinned baseline and `qwen3:4b` is the pinned challenger; the final model has not been selected. Never use a floating `latest` tag in any release script. Record every evaluated tag and selection status in the documented model manifest. All calls go through `backend/slm/client.py`, the only file in the whole backend allowed to talk to the local Ollama daemon (bound to loopback only — this is enforced by the Privacy lead's network-audit test).

## Schema-constrained output, not free-form chat

Every call uses the response model's JSON schema and `temperature=0` — this is deterministic, structured generation, not open-ended chat completion. The model receives a validated `EvidencePacket` (from the Statistics lead's contract) and must return `AssistantDraft` JSON matching its schema exactly. If it doesn't validate, that's a failure to handle, not something to silently patch around.

## The permitted/prohibited claim system

This is the actual safety mechanism — know it precisely, from `build-reference.md` Section 5.

**Permitted claim IDs:** `observation_of_deviation`, `within_person_association`, `trend_description`, `uncertainty_disclosure`, `not_enough_data`, `non_diagnostic_boundary`

**Prohibited claim IDs (must never appear in output):** `diagnosis`, `causal_explanation`, `treatment_or_crisis_advice`, `risk_prediction`

Example of permitted phrasing: *"Your unlock count was above your own recent baseline in the observed window, and there's a limited within-person association in this dataset."*
Example of prohibited phrasing: *"Your phone use caused your anxiety."* / *"You are depressed."* / *"You should seek treatment."*

## Two fallback templates — not one

Build both from Week 4, not improvised later:
1. A generic refusal/fallback for when the model output fails validation or the request is out of scope.
2. A **separate crisis-aware template** with real, reviewed helpline/support-resource content.

**Crisis wording is never generated by the model.** A rule-based detector (built with the Evaluation lead) triggers the pre-approved deterministic crisis message directly — this is safer and auditable than trusting the SLM to phrase a crisis response correctly under pressure.

## The deterministic safety gate

Every `AssistantDraft` is validated a second time, after generation, before it becomes an API response. Reject and rewrite to the safe fallback unless **all** of the following hold:
1. Every evidence ID referenced in the draft actually exists in the input packet.
2. Every claim ID used is approved by the specific evidence item it's attached to.
3. No prohibited claim ID or prohibited phrase class is present.
4. Every "ready" (non-fallback) explanation includes an uncertainty statement.

If validation fails for any reason, default to the safe fallback template — never let an unvalidated draft through because "it looked fine."

## Prompt versioning

Prompts live as YAML files in `backend/slm/prompts/`, loaded via `yaml.safe_load` into a strict Pydantic `PromptManifest` — never load YAML unsafely, and never inline-edit a prompt without going through the versioned file. Hash the loaded manifest and record the hash in every evidence/audit record, so any response is traceable back to the exact prompt version that produced it.

## What NOT to do

- Don't let the model see raw CES rows — only the validated `EvidencePacket`.
- Don't skip the second-pass safety validation "because the prompt already handles it" — the prompt is a request, not a guarantee.
- Don't hardcode crisis-response wording inline in Python — it lives in the versioned YAML template like everything else.
